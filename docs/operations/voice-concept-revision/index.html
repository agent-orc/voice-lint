Seven-day browser access

Pairing defaults to Remember this browser for 7 days. On the same local origin and browser profile, reload, reopening the browser and backend restart can resume access. The deadline is absolute and visits do not extend it. Log out revokes the remembered credential and associated runtime tokens for that browser. Browser enrollment, resume and logout require the exact origin and an intent header. API tokens stay in browser memory, outside URLs and localStorage. Definitive expiry returns all review components to pairing, with generation checks against late-response races. Reads may resume and retry once; writes and model starts are never replayed automatically.

Visual evidence includes the route, viewport, locale/theme/state, capture time and actual rendered build identity. Git is the preferred source of record. Versioned portable context, task results and decisions reference repository identity, requested ref, resolved commit and file hashes. Explicit working-copy snapshots retain their in-scope content, untracked files and deletions. Accepted, kept, rejected and deferred judgments retain reasons and input revisions. Changes to source, goals or applicable decisions trigger revalidation; older records stay historical. Private host paths, credentials and raw runtime data stay outside portable public records. Persistence does not automatically commit or publish.

How organisations enforce

GitLab, Red Hat, Grafana, Datadog and Elastic publish their rule sets and run them in CI. Four patterns recur.

  • Local equals CI. Contributors install the same linter version the pipeline runs, so a failure is reproducible before the push.
  • Three severities. Error for terminology and formatting, warning for style and tone, suggestion for readability. The graduated model avoids all-or-nothing gates over subjective calls.
  • Scoped escape hatches. Inline disable and enable comments around a passage, a project vocabulary for proper nouns, and a baseline for existing text. Never a global switch.
  • Foundation layering. A thin house style on top of the Google or Microsoft package instead of a rule set from scratch.

Kubernetes is the counter-example: a published style guide with no enforcement, framed as "use your best judgment". The Agent Orchestrator repositories are in the Kubernetes position today.

Claims

The most useful outside frame for the claim rules comes from advertising law rather than from style guides. The FTC requires a "reasonable basis" for every express or implied claim before it is made, and exempts vague puffery ("unmatched quality") because no reader relies on it. Specificity creates the obligation. The sober voice inverts the marketing use of that rule: it drops the puffery because it is empty, and keeps only specific claims because they can be backed. That is why §3 budgets claims and ties each one to a registry entry instead of counting adjectives.

German

Two registers must not be confused. Leichte Sprache is an accessibility register with mandatory layout rules for readers with learning disabilities. Einfache Sprache is standard German with short sentences and no jargon. The voice of this dossier is Einfache Sprache in a technical vocabulary. The German-specific failure mode is Nominalstil, the burying of verbs in nouns ("die Durchführung der Prüfung" for "die Prüfung durchführen"); Wortliga and TextLab flag it, no English guide has an equivalent rule. The German readability index with public adoption is the Hohenheimer Verständlichkeitsindex (0 to 20, web text at 16, specialist text at 12), a commercial composite of four validated formulas. Two of its components, Wiener Sachtextformel and LIX, are public closed-form formulas and can be implemented natively.

§5Markers of generated prose

Status 2026-09-03: Research complete. The findings are used to decide which markers become rules, which become density metrics, and which stay with a human or a judge.

The empirical literature on language-model prose has three strands, and they differ in how usable they are for a linter.

Vocabulary

Kobak et al. measured excess vocabulary in 14.2 million PubMed abstracts against a pre-2023 trend: "delves" at 25 times the expected rate, "showcasing" at 9, "underscores" at 9; 280 excess words in 2024, two thirds of them verbs. Liang et al. found "meticulous" 35 times, "intricate" 11 times and "commendable" 10 times more frequent in peer reviews. Juzek and Ward identified 21 focal words. Wikipedia's WikiProject AI Cleanup tracks the list by model generation and notes that it shifts: the 2023 words (delve, tapestry, testament) gave way to 2025 words (highlighting, showcasing, enhance). A static list goes stale within a year. No study of this kind exists for German; the German lists (nahtlos, ganzheitlich, "in der heutigen schnelllebigen Welt") are practitioner folklore.

For this project the vocabulary strand is necessary and insufficient. The Quality Studio page contains none of these words. Vocabulary rules catch a different author profile than the one at work here.

Two Vale packages exist for these tells (107 and 17 rules, MIT).

Statistics

Perplexity and burstiness (GPTZero), Binoculars, DetectGPT and Ghostbuster are document-level black boxes. They report a score, not a passage, and they carry a documented false-positive risk for non-native writers: Liang et al. found that more than half of TOEFL essays were classified as generated. Voice Lint's existing position is right: these methods do not become findings and do not enter CI. Three statistical measures are explainable and usable as metrics: nominalisation rate, lexical density with a register baseline, and the specificity proxy (numbers, dates, named entities per paragraph). Sentence length variance is computable without a model and stands in for burstiness.

What the alignment literature adds

RLHF training measurably produces longer, more repetitive and more detectable text, and rewriting by frontier models normalises voice: first-person pronouns and contractions decrease, word length and punctuation increase, even under prompts that ask to preserve voice. This is the mechanism behind the operator's complaint. Agents that write copy inherit a register, and an instruction in the prompt reduces the drift without removing its direction. That finding is the argument for detection after the fact rather than for better prompts alone.

Scoring

Three forms of score are conceivable. They are listed in the order in which they become defensible.

  • Status per dimension and per class (pass, warning, fail, insufficient evidence). Available from the first run. This is what a card gate and a CI check consume.
  • Length-normalised issue score after the first calibration round, in the Acrolinx form: words / (words + weighted issues) per family, weights from the dismissal rates. It orders documents for review and shows trends. It does not gate.
  • Calibrated 0 to 100 voice score only when the calibration package of the scoring contract exists: a held-out set of human judgements per language and text class, a published mapping, a regression test. For a single operator the honest expectation is that this stays null for a long time, and that the status view is what gets used.

Problematic texts are identified without any score: a document ranks by its count of error findings, then by the number of dimensions in fail, then by the structure density. That order surfaces the Quality Studio page first in every corpus measured here.

§8Enforcement: profile, prompts, gates

Status 2026-09-03: Only layer 1 exists (prompt pointer to the style guide). Layers 0, 2 and 3 are proposed. Cards VL-6, VL-7, VL-8, AGT-a and AGT-b in §11.

The operator asked for a reliable way to enforce the voice "through the prompts, the API and the rules of the Voice project". The evidence of §1 sets the requirement: the Quality Studio page was written while the canonical style guide had a "Public tone" section and while fifteen runtime prompt templates instructed agents to treat that guide as authoritative. The instruction did not hold. The alignment research in §5 explains why it cannot hold alone. Enforcement therefore has four layers, and only layer 2 is a gate.

Layer 0: profile and facts registry

The profile format of voice-lint already carries language, terms, avoided phrases, rule severities, examples and policy. The claim finder marks claim sentences; the matcher looks for a registry statement that covers the claim (token overlap first, judge for the remainder). A claim without a match is an error finding "unsupported claim". A matched claim whose fact has expired is a warning "stale fact". The registry is deliberately narrow: it verifies that the project has written down what it claims and when it last checked. It does not verify the world. This keeps voice-lint's stated non-goal (no general fact checking) and still catches "Founded 2026-07-11" and "covered by CI", because neither would be in a registry.

Layer 1: prompt contract

The pointer "consult the style guide" is replaced by a generated block of at most 40 lines that the prompt composer inserts for tasks touching repositories flagged as public copy. The block is generated from the profile so that prompt and gate never diverge. It states the twelve rules in one line each, shows five accepted and five rejected sentences from the profile examples, states the claim budget, and names the facts file. It ends with the instruction to run the self-check tool before reporting completion. Prevention is worth doing because it lowers the number of findings a gate has to bounce; it is not worth trusting.

Layer 2: detection

  • Pre-commit in the website and documentation repositories runs voice-lint check on changed files, the Vale pre-commit pattern.
  • CI in WEB, AOW and QSW runs the same check on push and pull request, fails on error findings, and publishes SARIF through reviewdog so findings appear as annotations. Vale's action is the model; local and CI versions are pinned to the same release.
  • Agent Studio gate step. Cards on repositories with publicCopy: true in the registry get a post-step that runs the check on the card's diff scope. Error findings send the card to review with the findings attached, the way test failures do today. The step reuses the existing gate executor; it needs no new pipeline concept.
  • MCP self-check. The voice-lint MCP tool (planned in the architecture) lets an agent lint its own draft before completion. The prompt block asks for it; the gate does not rely on it.

Layer 3: review

Voice Studio is described in §9. Its role in enforcement is calibration and exceptions: a human accepts or dismisses findings, waives a rule for a passage with a reason, maintains the facts registry, and turns a finding into a card when the fix is not a one-line edit.

Bounded rewrite loop for agents

When a gate bounces a text, the agent receives the JSON findings, rewrites the affected spans, and the check runs again. Two rounds are the cap. voice-lint's principle "analysis before rewriting" stays intact: the linter never rewrites; the agent or the human does, and the linter measures the result.

  • A scalar score never blocks; blocking needs concrete active findings; missing coverage is "incomplete", not a failure.
  • The repository profile cannot select providers, endpoints or credentials; the runtime configuration does.
  • strict_offline is the default and the CI mode.
  • Vale is the rule engine; native TypeScript metrics run on the internal document model.
  • The linter explains and measures; it does not rewrite.
  • Apache-2.0, English documentation, provenance for every imported rule.

§13JavaScript library and local Voice Studio

Design revision 2026-09-06: User direction: reusable JS library, primarily local use, a Studio that hosts website review, and Markdown support. Pilot: Quality Studio website. This section supersedes the delivery priority in §9–11. Implementation is pending.

One library, two ways to work

Voice Review is the proposed framework-independent JavaScript library. Embed it in an existing developer mode or mount it inside Voice Studio, a local web application with a source/address bar, website preview or Markdown renderer, and the same review panel. The overlay, annotations, analysis, proposals and storage contract are shared. Consumers can supply their own source and storage adapters.

Studio cannot inspect every cross-origin frame or override a site's embedding policy. A blocked URL offers an external browser, local-source connection or document import. The local pilot does not require a browser extension.

Keep the Specimen underlines

Select marked or unmarked text. The panel shows the exact quote, explanation, feedback type and comment. Save feedback first; request a proposal next. A proposal has a before/after comparison, a reason and its factual basis. “Confirm finding”, “Preview on page” and “Apply to local source” are distinct actions.

The daily workflow

  1. Open a local website or Markdown file in Studio, or enable the embedded developer mode.
  2. Analyze the current page or give feedback immediately. Manual review does not wait for an engine.
  3. Select a phrase, state what should change, and save. Reload or restart: the note remains.
  4. Request a focused suggestion, write your own replacement, or prepare a bounded agent request.
  5. Compare before and after in context. Apply only to the registered source version that was reviewed.
  6. Re-run checks, verify the meaning and rendering, then resolve the note. Publication follows the host workflow.

Metadata belongs to the content repository

One proposed .voice-lint/reviews/<document>.<locale>.voice-meta.json file holds stable annotation IDs, exact anchors, comments, editorial judgments, proposals and history. Saving is acknowledged only after a durable write. Revision conflicts, failed writes and stale proposals are visible. Browser storage is not the source of truth. Default analyzer logs remain content-free.

For the pilot, use the existing data-i18n keys such as stIntro, plus locale and source version. Store exact quote/context as a second anchor. Markdown uses a parsed source map and stable block identities. Reordering paragraphs must preserve notes; ambiguous matches require reattachment. Code, link destinations and Markdown syntax are excluded from prose analysis.

Suggestions and factual questions

Simple rule fixes and human-authored proposals work without a model. Richer agent proposals consume a bounded request containing selected units, comments, facts and acceptance criteria. They return a diff; they do not publish. A source change invalidates old proposal preconditions. Feedback becomes a profile example only through an explicit review of that change.

Correction to §7–8: absence from a facts registry means “unverified”, not “false”. Token overlap cannot establish truth. Such findings remain advisory unless a validated concrete rule and explicit policy justify stronger handling. Editorial state is separate from analyzer disposition and publication status.
